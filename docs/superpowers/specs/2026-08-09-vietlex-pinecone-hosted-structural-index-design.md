# VietLex Pinecone-Hosted Structural Index Design

**Date:** 2026-08-09

**Phase:** P3 — evidence-driven retrieval repair

**Status:** Approved for automatic local implementation by the user's current-task authorization. Remote pilot creation, full ingestion, and deletion remain separate operational gates.

## Problem and evidence

The P2 retrieval run is an honest failed baseline, not an accepted quality result. The 40 evaluated cases have 53 structurally verified evidence items. Every selected adjudication candidate is backed by the pinned local corpus, and the two target documents are present in the production Pinecone namespace with matching dataset revision and content SHA-256.

The failure is source retrieval:

- Document Recall@24 is `0/53` for all three P2 profiles.
- A read-only top-1000 probe found the target in only 11 of 40 cases.
- Twenty-nine targets were absent from top 1000.
- The best rank was 25, the median found rank was 236, and no target ranked within 24.
- Changing dense/sparse alpha from 0 to 1 on representative cases did not make the missing targets viable.

The current index stores one 384-dimensional vector per full legal document. Its dense representation is bounded to metadata, a partial outline, and an early body sample; its sparse representation is also bounded. Later articles are therefore not independently retrievable. Increasing top-k, changing reranker order, or enabling intent scoring cannot repair candidates that never enter source retrieval.

## User constraints

- Embeddings must be generated by a Pinecone-hosted model. No local embedding model may be used.
- A larger dimension than the current 384 is allowed and preferred when justified by measured quality and storage.
- The corpus may be reduced to fit Pinecone quota, but the reduction must follow a declared legal-scope predicate rather than the evaluation answers.
- Existing durable data must not be deleted before a replacement has passed a reproducible pilot and its rollback implications are understood.

## Options considered

### 1. Tune the existing v1 index

Rejected. The top-1000 probe shows that top-k, alpha, intent scoring, local chunk selection, and reranking operate too late or would require impractical candidate counts.

### 2. Stable integrated-embedding index with one record per document

Rejected as the target architecture. Pinecone would manage embeddings, but whole-document truncation would preserve the structural recall defect and integrated semantic-only records would not add article/body BM25.

### 3. Pinecone-hosted embeddings plus a structural document-schema index

Chosen. Pinecone Inference generates every passage/query vector. A Pinecone document-schema index stores one record per structural chunk with a 1024-dimensional dense field and a BM25-enabled body field. Semantic and lexical searches are run separately and merged deterministically before reranking.

This uses no local model. Standalone Pinecone Inference is selected instead of `create_index_for_model` because Pinecone's document-schema index currently does not accept an integrated `semantic_text` field.

## Model and dimension decision

A Pinecone-only smoke benchmark embedded the 40 real questions and 53 unique gold passages:

| Model | Dimension | Recall@1 | Recall@3 | MRR |
|---|---:|---:|---:|---:|
| `multilingual-e5-large` | 1024 | 0.925 | 1.000 | 0.9625 |
| `llama-text-embed-v2` | 768 | 0.975 | 1.000 | 0.9833 |
| `llama-text-embed-v2` | 1024 | 0.975 | 1.000 | 0.9833 |
| `llama-text-embed-v2` | 2048 | 1.000 | 1.000 | 1.0000 |

The selected pilot model is `llama-text-embed-v2` at 1024 dimensions with cosine similarity, `input_type=passage` for indexing, `input_type=query` for search, and fail-closed truncation accounting. It is materially larger than v1, empirically strong on the Vietnamese gold passages, and leaves more storage headroom than 2048. The smoke benchmark is a candidate-set test, not a corpus benchmark; it cannot authorize production cutover by itself.

## Corpus scope

### Pilot scope

The pilot includes every pinned-corpus document whose legal type is one of:

- `Hiến pháp` — 4 documents;
- `Luật` — 595 documents;
- `Pháp lệnh` — 228 documents.

This is an 827-document primary-legislation corpus, not a gold-document allowlist. It contains the two gold laws plus hundreds of real distractors. Selection is deterministic from the pinned local metadata and must record its predicate, dataset revision, selected document IDs hash, count by legal type, and content hashes.

### Expansion scope

If the pilot passes, the first full candidate scope adds:

- `Nghị định`;
- `Thông tư`;
- `Thông tư liên tịch`.

The resulting deterministic scope contains 25,937 documents and 0.979 GiB of raw content. The content store reports 45,624,399 sparse-preparation tokens, but `build_sparse_text()` truncates each document to at most 2,048 terms. Dividing that value by the chunk limit gives only a lower bound of 108,630 records, not a storage estimate. A real local smoke produced 1,748 structural records from the two gold laws alone, demonstrating that record counts are highly skewed. The pilot planner must enumerate the actual structural chunks before any quota or full-ingestion decision.

`Nghị quyết`, local `Quyết định`, `Công văn`, plans, notices, and other administrative material are excluded from the first expansion. They require a separate evaluation set and capacity decision; silently mixing selected local authorities would make scope hard to audit.

## Structural records

Documents are normalized and chunked with the existing legal-structure parser. The pilot record contract is:

- deterministic record ID derived from dataset repository, revision, document ID, and structural chunk identity;
- body text, limited to 420 approximate whitespace tokens with 48-token overlap only for oversized structural units;
- document ID, document number, title, source URL, legal type, issuing authority, issuance date;
- article, clause, heading path, citation;
- dataset revision, document content SHA-256, and structural chunk SHA-256;
- 1024-dimensional dense vector returned by Pinecone Inference using passage input.

No raw private user content is indexed. All text comes from the pinned public legal corpus.

## Pinecone index contract

The pilot uses a new index and namespace. It never reuses or clears v1.

- tentative index: `vietlex-legal-rag-v2-pilot`;
- namespace: `national-primary-v1`;
- document schema fields:
  - `body`: string with `full_text_search` enabled;
  - `embedding`: dense vector, dimension 1024, cosine;
- deletion protection: enabled after creation when supported by the selected API path;
- cloud/region: AWS `us-east-1`, matching Starter/Builder restrictions;
- API: Pinecone document schema API; its public-preview status and lack of backup support are explicit limitations.

Index creation, upsert, deletion, and cutover are separate commands. Dry-run and manifest generation are the defaults. Every mutating command requires an exact target index/namespace plus an explicit destructive or remote-write flag.

## Retrieval flow

1. Generate one query vector using Pinecone Inference with the exact configured model, dimension, and query input type.
2. Search the dense field for semantic candidates.
3. Search the BM25 body/title fields for lexical candidates.
4. Merge by deterministic reciprocal-rank fusion while retaining source ranks and scores.
5. Deduplicate by structural record ID, then balance by document.
6. Rerank a bounded merged set with the configured Pinecone-hosted multilingual reranker.
7. Return structural chunks directly; do not resolve full documents and re-chunk them again.

Exact document-number matches remain a separate deterministic lane and are merged first.

## Gates and failure behavior

### Local implementation gate

- pure corpus selector and structural record builder;
- deterministic manifest and storage estimate;
- Pinecone inference adapter with typed model/dimension/input contract;
- remote index adapter with dry-run default;
- runtime adapter behind an explicit v2 backend setting;
- no change to the default v1 backend before live pilot evidence exists.

### Pilot write gate

Before creating or writing a remote pilot:

- clean Git source provenance;
- exact index and namespace;
- model description fetched from Pinecone and contract-matched;
- selected corpus manifest passes hash/count/content integrity checks;
- projected records and embedding tokens fit configured safety budgets;
- remote mutation flag is explicit;
- v1 index is never modified.

### Cutover gate

Cutover requires, on an identical verified case set:

- non-zero Document/Article/Clause Recall and materially better recall than P2;
- candidate survival and technical-error reports at every stage;
- latency and Pinecone usage evidence;
- verified namespace count and sampled record/content hashes;
- storage extrapolation showing the expansion fits quota;
- a rollback plan.

### Deletion gate

No code path deletes v1 as part of ingestion or cutover. Deleting `vietlex-legal-rag-v1` requires a separate exact command naming that index after the replacement passes. A general migration flag cannot imply deletion.

## Testing and verification

- TDD unit tests for scope selection, deterministic IDs, chunk records, dimension checks, Pinecone response validation, dry-run behavior, and exact remote mutation gates.
- Contract tests with fake Pinecone clients; production code contains no fake provider implementation.
- Provider-free retrieval tests for dense/BM25 merge and structural output.
- A Pinecone-hosted inference smoke command that persists model specifications, token usage, raw ranks, and immutable comparison artifacts.
- Pilot evaluation uses the same 40 verified P2 cases plus a broader non-gold diagnostic set before any production claim.
- Focused, broader evaluation/ingestion, Ruff, compile, CRG review, and full pytest must pass before a commit is presented as implementation-complete.

## Known limitations

- The current 40-case verified set covers only two laws and cannot prove coverage of decrees or circulars.
- The Pinecone document-schema/FTS API is in public preview and does not support backups.
- Starter storage is capped across all indexes, so full v1 and full v2 may not coexist. The pilot must measure actual bytes per record before any deletion decision.
- Content-store sparse token counts are truncated preprocessing statistics and cannot be used to project structural record count. Full expansion capacity remains unknown until a provider-free structural enumeration completes.
- Corpus reduction improves capacity and focus but intentionally reduces document-type coverage. The application must expose the active corpus scope in runtime diagnostics and user-visible provenance.
